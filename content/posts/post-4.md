어디더라에서는 사용자가 SNS 링크를 공유하면 링크 속 콘텐츠를 읽고 장소 후보를 추출한다.

![](https://github.com/user-attachments/assets/55851c1d-4468-487c-a9b2-ce1b4531bc85)

이 부분이 어디더라의 핵심이다!

링크 하나를 분석하는 동안 크롤링, LLM 장소 추출, Instagram 이미지 OCR, Kakao 장소 검색 같은 작업이 실행된다.

문제는 대부분 `외부 서비스`에 의존한다는 점이다.

LLM 서버가 평소보다 느릴 수도 있고, Kakao API 응답이 늦을 수도 있다. Instagram 캡션만으로 장소를 찾지 못하면 이미지를 여러 장 가져와 OCR까지 돌려야 해서 처리 시간은 더 길어진다.

처음 링크 분석 기능을 설계할 때부터 이런 외부 작업이 끝날 때까지 사용자의 요청을 계속 붙잡아 두고 싶지 않았다.

그래서 Spring Backend는 분석 요청만 먼저 저장하고, 실제 링크 분석은 별도의 processing-server와 Worker에서 처리하도록 나눠 두었다.


# 비동기로 설계한 이유

![](https://github.com/user-attachments/assets/8dc8fc73-df8d-4e45-88a3-392e461667e1)


Spring Backend에서는 링크와 분석 요청을 하나의 트랜잭션으로 저장한다.

그리고 외부 processing job을 만드는 작업은 트랜잭션 안에서 바로 실행하지 않고 `AFTER_COMMIT` 이벤트 이후 전용 executor에서 실행하도록 했다.

만약 트랜잭션 안에서 외부 작업부터 만들어 버리면 이런 상황이 생길 수 있다.

```text
processing job 생성 성공
        ↓
DB 저장 중 오류 발생
        ↓
Transaction Rollback
```

그러면 DB에는 분석 요청이 없는데 processing-server에는 실행할 작업이 남아 버린다.

그래서 DB에 분석 요청이 정상적으로 기록된 경우에만 외부 작업이 만들어지도록 실행 시점을 Commit 이후로 옮겼다.

```text
DB 저장
  ↓
Commit 성공
  ↓
AFTER_COMMIT
  ↓
processing job 생성
```

다만 Spring 이벤트는 메모리 기반이라 Commit 직후 서버가 종료되면 이벤트가 실행되지 못할 수 있다.

이 경우에는 DB에 `PENDING`이나 `DISPATCHING`으로 남은 요청을 주기적으로 찾아 다시 processing-server로 보낸다.

Kafka 같은 durable message queue는 아니지만, 현재 규모에서 최대한 DB 상태를 기준으로 빠진 작업을 복구하도록 한 것이다.


## polling으로 설계한 이유

Frontend는 분석 상태가 `REQUESTED`나 `PROCESSING`인 동안 2초마다 상태를 조회한다.

`SUCCEEDED`, `FAILED`, `DISPATCH_FAILED`처럼 종료 상태가 되면 polling을 멈춘다.

Polling에는 분명 단점이 있다.

분석이 이미 끝났더라도 Frontend가 다음 상태 조회를 보내기 전까지 알 수 없기 때문에 최대 약 2초의 결과 감지 지연이 생긴다. 상태 조회 요청도 반복해서 발생한다.

그런데 현재는 분석 완료 여부만 알면 되고, 단계별 진행 상황을 실시간으로 보여 줄 필요까지는 없었다.

같은 job의 상태 조회가 동시에 들어오면 single-flight로 하나의 요청만 processing-server에 보내고, 결과는 2초 동안 cache한다.

Spring Backend가 Frontend와 SSE 연결을 유지한다고 해도 Worker에서 분석 상태가 변경되었다는 사실을 Spring에게 어떻게 전달할 것인지가 또 필요하다. Callback을 추가할 수도 있고, Redis Pub/Sub 같은 별도의 전달 경로를 둘 수도 있다. 따라서 비교적 단순하게 구현할 수 있던 polling으로 진행했다.

향후에는 분석 단계나 진행률을 실시간으로 보여 주고 싶을 때 SSE 도입을 고려해 볼 수 있을 것 같다.

현재는 별도의 진행률을 보여 주지 않고, 분석을 기다리는 동안 "조금만 더 기다리면 끝나요!" 같은 미리 작성해 둔 문구를 랜덤으로 보여 주는 정도니까... (실제로 팀원분이 "이거 진짜 진행 상황에 맞춰서 문구가 나오는 거예요?!"라고 신기해하셨는데, 사실 그냥 랜덤 문구라 괜히 조금 마음이 쓰였다...ㅎㅎ;;)

# 어디를 개선할 수 있을까?

사실 processing-server는 본인이 작업한 부분이 많지 않다.

SNS 타입별로 콘텐츠를 크롤링하는 부분까지만 구현했고, 이후 장소를 추출하고 보강하는 과정은 다른 팀원분께서 맡아주셨다.

그래서 이번에 리팩토링하면서 Worker 코드를 처음 본다. (자랑이다!)

기존 로그에서는 작업 전체의 `elapsed_ms`와 성공률, timeout 정도만 확인할 수 있었다.

그래서 Worker 작업을 단계별로 나누어 한 줄의 구조화된 로그에 기록하도록 했다.

```text
job_age_at_claim_ms
cooldown_lookup_ms
crawl_ms
extraction_pipeline_ms
image_fetch_ms
ocr_ms
kakao_enrichment_ms
persist_ms
```

`job_age_at_claim_ms`는 job이 만들어진 뒤 Worker가 가져가기 전까지 Queue에서 기다린 시간이다.

전체 시간만 보는 게 아니라 Queue가 밀린 것인지, 특정 외부 호출이 느린 것인지 나눠서 볼 수 있게 했다.


## 레거시가 남아버렸다 - !

기존에는 LLM에 이런 형식을 요청했다.

```json
{
  "store_name": "청춘1번가",
  "address": "서울 동대문구 ...",
  "store_name_evidence": "청춘1번가",
  "address_evidence": "서울 동대문구 ...",
  "certainty": "high",
  "places": [
    {
      "store_name": "청춘1번가",
      "address": "서울 동대문구 ...",
      "store_name_evidence": "청춘1번가",
      "address_evidence": "서울 동대문구 ...",
      "certainty": "high"
    }
  ]
}
```

처음에는 한 장소만 반환하던 구조였고, 기획이 바뀌며 여러 장소를 지원하면서 `places`가 추가됐다.

기존 저장 구조를 바로 바꾸지 않기 위해 최상위 필드는 남겼는데, 그 값까지 LLM에게 다시 만들라고 하고 있었다.

`evidence`도 LLM이 새로 판단할 값은 아니다. LLM이 뽑은 장소명과 주소가 원문에 실제로 있는지 Python에서 찾으면 된다.

그래서 LLM에는 분석에 필요한 값만 요청하도록 바꿨다.

```json
{
  "places": [
    {
      "name": "청춘1번가",
      "address": "서울 동대문구 ..."
    }
  ]
}
```

기존 응답에서 최상위의 `store_name`, `address`, `store_name_evidence`, `address_evidence`, `certainty`는 `places[0]`과 같은 첫 번째 장소를 표현하는 legacy 필드였다.

장소가 12개라면 LLM은 첫 번째 장소를 나타내는 최상위 필드 5개와 `places`에 포함된 12개 장소의 필드 60개(12 × 5)를 합쳐 총 65개의 scalar field를 생성했다.

이 구조에서는 첫 번째 장소 정보가 최상위와 `places[0]`에 중복으로 생성됐다.

이제는 장소마다 `name`과 `address`만 요청하므로 12개 장소에 대해 총 24개(12 × 2)의 scalar field만 생성한다.

LLM이 생성하는 scalar field 수는 65개에서 24개로 약 63.08% 줄었다.

다만 이 수치를 그대로 추론 시간 감소율이라고 볼 수는 없다. 실제 처리 시간은 입력 길이, 출력 token 수, 모델의 응답 속도, 외부 서버와 네트워크 상태 등의 영향도 받기 때문이다.

그래도 실제 처리 시간에는 차이가 있는지 궁금해서 로컬에서 이전과 동일한 콘텐츠를 다시 분석해 봤다.

```text
이전  16.719초
현재   8.937초
차이   7.782초
```

같은 입력에서 전체 처리 시간이 약 46.5% 줄었고, 처리 속도는 약 1.87배가 됐다.

오... 생각보다 많이 줄었다!

입력 콘텐츠가 같기 때문에 게시물 길이나 추출 장소 수가 달라서 생긴 차이는 아니다.

다만 외부 LLM 서버 상태와 네트워크 상태까지 완전히 같았던 것은 아니다.

지금 말할 수 있는 것은 **동일 콘텐츠를 리팩토링 전후로 분석했을 때 전체 처리 시간이 16.719초에서 8.937초로 줄었다**는 것까지다. 이후 같은 입력의 `extraction_pipeline_ms`와 전체 처리 시간도 몇 차례 더 남겨 보면 어느 단계에서 실제로 줄었는지 더 정확하게 확인할 수 있을 것 같다.

`certainty`도 확인해 보니 실제 분석에는 사용되지 않았다.

그렇다면 LLM이 스스로 매긴 certainty를 굳이 생성하고 저장할 이유가 없었다.

`store_name_evidence`와 `address_evidence`는 원문에서 정확히 일치하는 문자열만 찾는다. `#플루밍`처럼 해시태그로 적혀 있다면 원문 표기를 우선하고, 원문에 없는 값은 evidence로 만들어 내지 않는다.

기존 LLM 응답 형식을 읽는 코드도 삭제했다.

LLM 원본 응답은 DB에 저장하거나 다른 버전의 Worker와 주고받는 값이 아니다. 요청을 보낸 Worker가 그 자리에서 바로 파싱하므로 배포 호환성을 위해 이전 형식을 유지할 이유가 없었다.

이번에는 **판단 규칙은 그대로 두고 출력 계약과 내부 중복만 줄였다.** 장소명과 주소가 원래 순서대로 도메인에 들어가는지, evidence가 원문에 있는 값으로만 만들어지는지는 회귀 테스트로 남겼다.


## 분석이 직렬로 실행되고 있었다..!!

사실 processing-server는 본인이 작업한 부분이 많지 않다.

SNS 타입별로 콘텐츠를 크롤링하는 부분까지만 구현했고, 이후 장소를 추출하고 보강하는 과정은 다른 팀원분께서 맡아주셨다.

그래서 이번에 리팩토링하면서 Worker 코드를 처음 본다.

Processing Worker 코드는 대부분 `async def`로 작성되어 있었다.

Kakao 장소 보강 부분을 보다가 이런 코드를 발견했다.

```python
for extracted_place in extracted_places:
    places = await search_places(extracted_place)
```

장소 후보를 하나씩 돌면서 search_places()의 결과를 바로 await하고 있었다.

이렇게 되면 첫 번째 장소 검색이 끝나야 반복문의 다음 단계로 넘어가고, 그제야 두 번째 장소 검색을 시작한다.

즉, 장소 A의 Kakao 검색이 끝나야 B를 시작하고, B가 끝나야 C를 시작한다.

한 링크에서 추출되는 장소가 많아질수록 Kakao enrichment 시간도 각 후보의 호출시간을 더한 값에 가까워질 수 있다.

장소 A의 검색 결과가 장소 B나 C의 검색에 영향을 주지 않는데... 굳이 앞의 요청이 끝날 때까지 하나씩 기다려야 하나?

`await`로 기다리는 동안 이벤트 루프가 다른 코루틴을 처리할 수는 있지만, 위 반복문은 A가 끝나야 다음 반복으로 넘어가 B를 시작한다.

그래서 이미 LLM이 뽑아 준 장소 후보끼리만 `asyncio.gather()`로 함께 실행하도록 바꿨다.

```text
크롤링 → LLM 추출 → Kakao 검색
```

이 순서는 서로 의존하므로 그대로 유지한다.

반면 LLM이 뽑아 준 A, B, C의 Kakao 검색은 서로 독립적이므로 기다리는 시간을 겹칠 수 있다.


# 후보를 동시에 보낸다면?

현재 어디더라는 한 링크에서 추출하는 장소 후보를 최대 12개로 막아 두고 있다.

12라는 숫자는 성능 테스트를 통해 찾아낸 한계값은 아니다. 당시 팀원들과 실제 게시물에 포함될 만한 장소 수를 생각해 보고, 너무 많은 장소가 들어 있는 게시물까지 전부 분석하는 것은 현실적으로 어렵다고 판단해 기획 단계에서 정한 상한이다.

Instagram 카드 뉴스처럼 TOP 30, TOP 100을 소개하는 게시물이 있어도 실제 검색 후보는 최대 12개까지만 넘어온다.

한 게시물에 포함된 장소를 끝없이 추출하고 외부 API로 검색해 줄 수는 없었다. LLM, OCR, Kakao API 모두 호출에 비용이 들기 때문이다.

이처럼 후보 수의 상한이 정해져 있으니 병렬 처리의 최대 범위도 예측할 수 있었다. 한 job이 다루는 후보는 최대 12개이므로, 모든 후보를 동시에 검색하더라도 job 하나가 만들어 내는 동시 작업은 12개를 넘지 않는다. 이 범위 안에서 순차 처리로 발생하던 대기 시간을 줄이기로 했다.

동시성을 높인다고 전체 API 호출 횟수가 줄어드는 것은 아니다. 같은 요청을 하나씩 보낼지, 대기 시간이 겹치도록 보낼지의 차이다. 따라서 호출 비용은 그대로 유지하면서 한 job의 전체 처리 시간을 단축하는 것이 이번 변경의 목적이었다.

이를 위해 Semaphore와 HTTP connection pool의 크기를 모두 12로 설정했다. Semaphore는 동시에 실행되는 검색 작업 수를 제한하고, connection pool은 실제로 열 수 있는 HTTP 연결 수를 제한한다. 두 설정을 후보 상한과 맞춤으로써 한 job의 대기 시간은 줄이되 현재 기획 범위를 넘어서는 요청이 동시에 실행되지 않도록 했다.

동시 처리에서는 요청이 시작된 순서와 완료되는 순서가 달라질 수 있다. 하지만 asyncio.gather()는 작업이 B, C, A 순서로 완료되더라도 결과를 입력 순서인 A, B, C로 반환한다. 덕분에 기존 deduplication 로직과 최종 장소 순서는 그대로 유지할 수 있었다.

또한 장소 하나를 검색하는 과정에서 일시적인 오류가 발생하더라도 전체 작업을 실패시키지 않는다. 실패한 후보만 제외하고 나머지 검색 결과는 정상적으로 반환하도록 오류를 격리했다.

## 후보 하나에서 불필요하게 검색하던 것도 줄였다

기존 로직은 검색에 실패할 때마다 주소 범위를 바꿔 가며 재검색했다.

```text
장소명 + 주소 조합으로 최대 4회 검색
모두 실패하면 장소명만으로 1회 검색
그래도 실패하면 마지막으로 주소만 바꿔 가며 최대 4회 검색
```

따라서 최악의 경우 후보 하나를 처리하는 데 `4 + 1 + 4 = 9회`까지 Kakao API를 호출할 수 있었다.

문제는 '주소'만 검색하는 과정이었다.

이미 장소명 + 전체 주소처럼 더 많은 정보를 포함한 검색에서도 적절한 장소를 찾지 못했는데, 장소명까지 제거한 채 주소만으로 다시 검색한다고 해서 원하는 결과를 찾을 가능성이 높아지는 것은 아니었다.

오히려 주소만으로 검색하면 같은 건물이나 인근의 다른 장소가 결과에 포함될 가능성이 커진다. 설령 검색 결과가 나오더라도 원래 찾으려던 장소인지 판단하기 어려워 최종 후보로 선택할 수 없는 결과가 될 수 있었다.

즉, API 호출 횟수만 늘리고 실제 매칭에는 거의 기여하지 않는 fallback이라고 판단했다.

그래서 검색 전략을 단순화했다.

장소명은 모든 검색에서 유지하고, 검색에 실패할 때 주소 범위만 점진적으로 넓히도록 변경했다.

```text
장소명 + 전체 주소
→ 장소명 + 도로
→ 장소명 + 동·읍·면
→ 장소명 + 구·군·시
→ 장소명만
```

confidence가 `0.9` 이상인 결과를 찾으면 바로 끝낸다.

`0.7~0.9`의 애매한 결과는 일단 들고 있다가 다음 검색에서 더 좋은 결과가 나오면 바꾼다.


confidence 계산에서 `포은로8길`의 숫자 8을 건물 번호로 잘못 보던 부분도 독립된 건물 번호 token인지 확인하도록 바꿨다.

`망원시장`과 `민영활어공장 망원시장점`처럼 이름 일부가 포함된 경우도 정확 일치나 정상적인 지점 suffix보다 낮게 평가하도록 했다.


## 테스트로 확인한 것

이번 테스트에서는 크게 세 가지를 확인했다.

1. **독립적인 Kakao API 호출을 병렬화했을 때 실제 대기 시간이 줄어드는가**
2. **설정한 동시성 상한이 실제 실행에서도 지켜지는가**
3. **검색 전략을 줄여도 정확도를 유지하면서 불필요한 API 호출을 줄일 수 있는가**

### 1. 외부 호출은 실제로 병렬화되는가

먼저 장소 후보 12개와 호출당 50ms의 고정 지연을 사용해 동시성 `1`, `3`, `6`, `12`를 각각 30회씩 비교했다.

| 동시성 | 실제 최대 동시 실행 수 |      p50 |      p95 | 직렬 대비 p95 감소 |
| -- | ------------ | ------- | ------- | ----------- |
|   1 |             1 | 732.44ms | 736.83ms |            - |
|   3 |             3 | 243.33ms | 245.86ms |       66.63% |
|   6 |             6 | 121.60ms | 123.83ms |       83.19% |
|  12 |            12 |  60.99ms |  62.00ms |       91.59% |

동시성이 증가할수록 전체 처리 시간이 거의 비례해서 감소했고, 실제 최대 동시 실행 수도 각각 `1`, `3`, `6`, `12`로 설정값을 넘지 않았다.

고정 지연 50ms를 제외하면 로컬 연산량 자체는 동시성 1과 12에서 크게 다르지 않다. 즉, CPU 연산이 빨라진 것이 아니라 **독립적인 외부 호출의 대기 시간이 서로 겹쳐졌다.**

따라서 **외부 I/O를 병렬화하면 대기 시간을 실질적으로 줄일 수 있고, 동시에 설정한 concurrency limit도 정상적으로 적용된다는 것**을 확인했다.

### 2. 실제 Kakao API에서도 같은 효과가 있는가

고정 지연만으로는 실제 네트워크 환경을 반영하지 못하므로, 공개 장소 12개를 대상으로 Kakao API도 직접 호출했다.

각 동시성 조건을 세 번씩 실행해 총 144회의 API 요청을 측정했다.

| 동시성 | 호출 수 | batch p50 | batch p95 | HTTP 성공 | 결과 있음 | 오류 |
|---|---|---|---|---|---|
| 1 | 36 | 525.70ms | 874.32ms | 36 | 33 | 0 |
| 3 | 36 | 201.08ms | 210.42ms | 36 | 33 | 0 |
| 6 | 36 | 109.22ms | 124.74ms | 36 | 33 | 0 |
| 12 | 36 | 68.06ms | 97.77ms | 36 | 33 | 0 |

동시성 1의 batch p95는 `874.32ms`였지만 동시성 12에서는 `97.77ms`까지 감소했다. 이번 측정 범위에서는 동시성 12까지 `429`, timeout, connection error도 발생하지 않았다.

따라서 **현재 수준의 단일 Worker에서는 후보별 Kakao 검색을 직렬로 처리할 이유가 크지 않았고, 제한된 범위 안에서 병렬화하는 편이 훨씬 효율적이었다.**

다만 각 조건을 세 번씩만 실행한 소규모 테스트이므로, 이것이 동시성 12가 항상 안전하다는 의미는 아니다. Worker 수가 늘어나면 프로세스 전체의 동시 요청 수 역시 함께 증가하기 때문에, 운영 환경에서는 rate limit과 timeout을 계속 관찰해야 한다.

### 3. 검색 횟수를 줄여도 결과 품질을 유지할 수 있는가

검색 전략 자체도 이전 방식과 비교했다.

응답을 고정한 세 가지 상황을 만들어 기존 로직과 개선한 로직의 선택 결과와 API 호출 횟수를 확인했다.

| 상황                     |          기존 |        개선 후 | 결과                |
| ---------------------- | ---------- | ---------- | ----------------- |
| 첫 검색에서 confidence 0.95 |          1회 |          1회 | 이미 좋은 결과면 즉시 종료   |
| 첫 결과 0.75, 다음 결과 0.95  | 1회, 0.75 선택 | 2회, 0.95 선택 | 더 정확한 결과 선택       |
| 모든 검색 실패               |          9회 |          5회 | 최대 호출 수 44.44% 감소 |

기존 방식은 첫 번째 검색 결과가 일정 기준을 넘으면 그대로 선택했기 때문에, 뒤에서 더 정확한 결과를 찾을 가능성을 놓칠 수 있었다.

개선 후에는 충분히 높은 confidence가 나올 때까지 주소 범위를 조정하며 검색하되, 의미 없는 `주소만 검색` fallback은 제거했다.

그 결과 **더 좋은 후보를 선택할 수 있는 여지는 유지하면서, 최악의 경우 API 호출 횟수는 9회에서 5회로 44.44% 줄었다.**

실제 Kakao API에서도 공개 장소 12개를 골라 확인했다.

12개 모두 기대한 장소와 행정구역이 일치했고, 전체 API 시도 횟수는 20회였다. 후보 하나당 검색 시도 횟수의 중앙값은 1회였다.

즉, 테스트한 사례에서는 **대부분 첫 검색만으로 충분한 결과를 얻었고, fallback은 필요한 경우에만 추가로 실행됐다.**

물론 이 결과가 전체 장소 검색 정확도가 100%라는 의미는 아니다. 제한된 표본으로 전체 입력 분포를 대표할 수는 없다...

결론은,

> 후보별 Kakao 검색은 제한된 동시성으로 병렬화했을 때 대기 시간을 크게 줄일 수 있었고, 검색 fallback을 단순화한 뒤에도 테스트한 장소의 결과 품질을 유지하면서 최대 API 호출 수를 줄일 수 있었다.

# 결론 - 結論なのだ！

기존에 구현했던 비동기 job과 polling을 새롭게 막 바꾸지는 않았다.

대신 그 안의 처리 과정을 다시 보면서 사소하게 개선해나갔다.

* LLM 출력을 `places[].name/address`로 줄이고, 사용하지 않던 `certainty`와 중복 legacy field를 도메인에서도 없앴다.
* evidence는 LLM에게 생성시키지 않고 Python이 원문에서 찾도록 바꿨다.
* 서로 독립적인 Kakao 검색과 이미지 OCR의 대기 시간을 제한된 동시 실행으로 겹쳤다.
* 선택될 수 없는 주소-only 검색을 없애 후보당 최악의 Kakao 호출 수를 9회에서 5회로 줄였다.
* 애매한 첫 결과보다 더 정확한 다음 결과를 선택할 수 있게 검색 종료 기준을 바꿨다.
* 단계별 처리 시간과 Queue 대기 시간을 로그로 남겼다.
* 외부 HTTP connection과 동시 실행 코드를 재사용할 수 있게 정리했다.

**서로 의존하는 작업의 순서는 그대로 지키고, 서로 독립적인 외부 호출의 기다리는 시간만 겹쳤다. 분석에 필요한 값과 검색은 남기고, 결과에 쓰이지 않는 출력과 API 호출은 줄였다.**
