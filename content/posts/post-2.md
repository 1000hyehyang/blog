# 장소가 계속 쌓여도 괜찮을까?

어디더라에서는 커플이나 친구끼리 하나의 Room을 만든다.

![udidura-room](https://github.com/user-attachments/assets/804fd85b-907a-4dff-8225-e5de37369d06)

SNS 게시물에서 추출한 장소도 Room에 저장되고, 사용자가 직접 검색한 장소도 같은 Room에 저장된다. 이렇게 모인 장소는 목록으로 확인하거나 지도 위에 마커로 표시할 수 있고, 데이트 코스를 생성할 때 후보 장소로도 사용된다.

그러니까 사용자가 방에 들어왔을 때 자주 호출되는 API 중 하나가 장소 목록 조회 API다.

```http
GET /api/v1/rooms/{roomId}/places
```

장소 목록은 최신순으로 정렬된다.

```sql
ORDER BY created_at DESC, id DESC
```

한 번에 모든 장소를 가져오지는 않는다. 커서 페이지네이션을 이용해 기본 20개씩 조회하고, 다음 페이지가 있는지 확인하기 위해 실제로는 21개를 가져오도록 구현했다.

```sql
LIMIT 21
```

프로젝트를 기획하던 초반, Room과 장소 저장 정책을 정리하면서 팀원들 사이에서 이런 이야기가 나온 적이 있다.

> 그런데 Room 하나에는 장소를 몇 개까지 저장할 수 있게 할까요?

사용자가 계속해서 장소를 저장할 수 있다면, 언젠가는 Room 하나에 데이터가 너무 많이 쌓일 수도 있었다. 그렇다고 장소를 무제한으로 저장하게 두면 뭔가뭔가... 조회가 무거워질 것 같은 기분이 들어서 찜찜했다.

그래서 팀원들과 대략적인 숫자를 이야기해 보았다.

“내가 사용자라면 200개 정도 저장하지 않을까?”

“그래도 오래 사용하면 500개까지는 갈 수도 있지 않을까?”

대충 이런 식으로 상한 후보가 나왔다.

그런데 사실, 실제 사용자가 장소를 얼마나 저장하는지 확인한 데이터도 없었고, Room에 장소가 몇 개까지 쌓였을 때 성능 문제가 발생하는지도 측정해 본 적이 없었으니 근거가 있다고 말할 순 없었다. 단지 각자 사용자의 입장에서 생각했을 때 이 정도면 충분하지 않을까 하고 추측한 숫자니까...

결국 당시에는 Room 전체의 저장 상한을 정하지 않기로 했다.

종합설계 프로젝트에서는 정해진 기간 안에 기능을 완성하는 것이 최우선이니까. 정상적인 테스트 범위 안에서는 누적 저장 상한이 없어도 서비스가 동작했기 때문에, 요청 한 번에 저장하거나 조회할 수 있는 개수만 제한하고 Room 전체의 상한은 추후 리팩토링 사항으로 남겨 두었다.

그리고 이번에 그때 미뤄 두었던 질문을 다시 꺼내 보기로 했다.

> 하나의 Room에는 장소를 몇 개까지 저장할 수 있어야 할까?

현재 구현에는 Room 전체의 장소 개수에 대한 제한이 없다. 사용자는 이론상 하나의 Room에 장소를 1,000개든 10,000개든 계속 저장할 수 있다.

물론 실제로 장소를 10,000개나 저장할 사용자가 있을지는 모르겠다.

하지만 아마 그런 사용자는 없을 것이다라는 생각만으로 제한이 필요 없다고 결론 내리는 건 내키지 않았다. 반대로 별다른 근거 없이 당시 이야기했던 200개나 500개로 막아 버리는 것도 과연 옳은 방식인지 의문이 들었다.

그래서 장소가 계속 쌓일 때 실제로 무엇이 느려지는지 확인한 뒤, 저장 상한이 정말 필요한지 판단해 보기로 했다.

## 데이터가 쌓이면 구체적으로 무엇이 문제가 될까?

처음에는 막연하게 `데이터가 많아지면 느려지지 않을까?`라고 생각했다.

하지만 무엇이 어떻게 느려질 수 있는지를 구분하지 않고서는 제대로 테스트하기 어려웠다.

그래서 Room의 장소가 많아질 때 발생할 수 있을 것 같은 문제를 먼저 정리해 보았다.

1. 원하는 Room의 데이터를 찾기 위해 더 많은 행을 읽을 수 있다.
2. 최신순으로 가져오기 위해 별도의 Sort가 발생할 수 있다.
3. 전체 장소 개수를 구하는 count 쿼리의 비용이 증가할 수 있다.
4. 지도나 코스 생성처럼 여러 장소를 한 번에 다루는 기능의 메모리 사용량과 연산량이 증가할 수 있다.
5. 테이블과 인덱스가 커지면서 저장 공간이나 VACUUM, 백업과 복구에 필요한 비용도 증가할 수 있다.

다만 장소 목록 API는 커서 페이지네이션으로 20개씩만 가져온다.

Room에 장소가 10,000개 있다고 해서 매 요청마다 10,000개를 모두 애플리케이션 메모리에 올리는 구조는 아니다.

따라서 인덱스와 커서 조건이 본인이 의도한 대로 동작한다면, Room 전체 장소 수가 늘어나더라도 목록 조회 시간은 크게 변하지 않을 수도 있다.

반면 지도나 데이트 코스 생성처럼 Room에 저장된 여러 장소를 한꺼번에 사용하는 기능은 상황이 다르지 않을까?

우선 이번 글에서는 가장 자주 호출되는 장소 목록 API부터 확인하기로 했다.


## 이미 인덱스가 있는데도 확인해야 할까?

장소 목록을 구현할 때 Room ID로 장소를 찾고, 생성 시각과 ID를 기준으로 최신순 정렬한다는 점을 고려해 `RoomPlace`에 복합 인덱스를 정의해 두었다.

```java
@Index(
    name = "idx_room_places_room_created_id_desc",
    columnList = "room_id, created_at, id"
)
```

당시에는 조회 조건과 정렬 조건에 맞춰 인덱스를 구성했으니, 장소가 늘어나도 어느 정도는 대응할 수 있을 것이라고 생각했다.

커서 페이지네이션도 적용해 두었으니 목록 조회 자체에는 큰 문제가 없을 것 같았다.

그런데 `인덱스를 작성해 두었다`는 것과 `내가 의도한 방식으로 실제 DB에서 사용되고 있다`는 것은 다른 이야기라는 사실을 알게 되었다.

엔티티에 인덱스를 선언했더라도 실제 DB에 생성되어 있는지 확인해야 한다. 인덱스가 존재하더라도 PostgreSQL이 해당 쿼리에서 다른 실행 방법이 더 저렴하다고 판단하면 사용하지 않을 수도 있다.

즉, 인덱스가 실제 목록 조회에서 어떤 역할을 하고 있는지 확인하려면 쿼리가 실행되는 방식을 직접 살펴봐야 했다.

그래서 이번에 처음으로 `EXPLAIN ANALYZE`를 사용해 보기로 했다.

# EXPLAIN ANALYZE

https://www.postgresql.org/docs/17/using-explain.html

솔직히 이전까지 `EXPLAIN`이 정확히 무엇을 보여주는지 잘 알지 못했다.

쿼리 앞에 붙이면 DB가 어떻게 조회하는지 보여주고, 성능을 분석할 때 사용한다는 정도만 알고 있었다.

내가 이해한 범위에서 `EXPLAIN`은 PostgreSQL이 해당 쿼리를 어떤 순서와 방법으로 실행하려고 하는지 보여주는 기능이다.

테이블의 행을 순서대로 읽는 계획이라면 `Seq Scan`, 인덱스를 이용한다면 `Index Scan`이나 `Index Only Scan`이 나타난다. 조회된 데이터를 원하는 순서로 다시 정렬해야 한다면 `Sort`도 실행 계획에 표시된다.

기본 `EXPLAIN`은 계획을 보여 준다.

본인은 실제 실행 시간과 행 수, 버퍼 사용량까지 보기 위해 `ANALYZE`와 `BUFFERS`를 함께 사용했다.

먼저 다른 연관 데이터는 제외하고, `room_places` 테이블에서 목록을 가져오는 핵심 부분만 확인했다.

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT rp.id, rp.created_at
FROM room_places rp
WHERE rp.room_id = :room_id
ORDER BY rp.created_at DESC, rp.id DESC
LIMIT 21;
```

실제 API에서는 장소와 카테고리, 태그를 함께 가져오는 fetch join 쿼리를 실행한다. 전체 장소 개수를 응답에 포함하기 위한 count 쿼리도 별도로 실행한다.

처음부터 모든 비용을 한꺼번에 측정하면 어느 부분에서 차이가 발생하는지 알기 어려울 것 같았다.

그래서 다음과 같이 세 단계로 나누어 확인했다.

1. `RoomPlace` 핵심 목록 쿼리
2. Room의 전체 장소 개수를 구하는 count 쿼리
3. Spring Boot를 거쳐 JSON 응답까지 반환하는 실제 API

## 테스트 방법

처음 정한 데이터 구간은 다음과 같았다.

```text
50 → 100 → 200 → 500 → 1,000
```

50개와 100개는 일반 사용자도 충분히 도달할 수 있을 것 같은 구간으로 잡았다.

200개와 500개는 프로젝트를 개발할 당시 팀원들과 저장 상한을 고민하면서 후보로 이야기했던 숫자다.

1,000개는 별도의 제한을 두지 않았을 때를 확인하기 위한 과한 구간으로 잡았다.

그런데 1,000개까지 테스트를 마치고 보니 새로운 의문이 생겼다.

> 1,000개도 빠르다면...?

Room에 1,000개를 저장하는 상황을 이미 과하다고 생각했지만, 이왕 확인하는 김에 그보다 훨씬 큰 데이터에서도 경향이 달라지는지 보고 싶었다. (실제 유저가 Room에 장소를 1,000개 이상이나 넣는 상황을 가정하는 게 웃기긴 하지만!)

그래서 최종적으로 한 Room에 장소를 10,000개까지 넣어 보았다.

또 하나의 Room에만 데이터가 많은 상황과 전체 테이블에 여러 Room의 데이터가 많이 쌓인 상황은 다를 수 있다고 생각했다.

이를 확인하기 위해 조회 대상 Room에는 장소를 200개만 넣고, 별도의 Room에 10,000개를 넣는 테스트도 추가했다.

측정 조건은 다음과 같다.

* PostgreSQL 17.8 Docker
* 로컬에서 실행 중인 Spring Boot 애플리케이션
* 각 구간 실행 전 `ANALYZE`
* 첫 20회 요청은 워밍업으로 제외
* 이후 100회씩 3세트 측정
* p50, p95, p99는 세 세트 결과의 중간값 사용
* `EXPLAIN ANALYZE`는 5회 실행 후 실행 시간의 중앙값 사용
* 요청은 한 번에 하나씩 보내는 순차 테스트
* DB와 애플리케이션이 같은 PC에 있는 localhost 환경

처음에는 각 구간마다 데이터를 삭제한 뒤 다시 삽입하는 방식으로 측정했다.

그런데 테스트를 반복하다 보니 뒤쪽 실험에서 실행 시간과 버퍼 결과가 예상보다 불규칙하게 나타났다.

찾아보니 PostgreSQL에서는 데이터를 삭제해도 곧바로 디스크 공간이 완전히 정리되는 것은 아니며, dead tuple이나 비어 있는 페이지가 남아 후속 측정에 영향을 줄 수 있다고 했다.

그래서 최종 측정은 로컬 DB에서 `VACUUM FULL`을 실행한 뒤, 50개부터 데이터를 누적해서 추가하는 방식으로 다시 진행했다.

물론 이것이 완벽한 측정 방법인지는 확신할 수 없다.

다만 앞선 테스트의 삭제 흔적이 뒤쪽 결과에 영향을 주는 상황은 조금 줄일 수 있을 것이라고 판단했다.

이번 테스트는 운영 환경을 재현한 부하 테스트가 아니다.

모바일 네트워크 지연도 포함되지 않았고, 여러 사용자가 동시에 요청하는 상황도 확인하지 않았다. 현재 본인이 작성한 코드에서 데이터 개수가 증가할 때 어떤 경향이 나타나는지를 확인하기 위한 로컬 실험에 가깝다.

## 우선 DB 쿼리는 어떻게 변했을까?

핵심 목록 쿼리의 결과는 다음과 같았다.

| Room 장소 수 | 실행 계획           | 별도 Sort | 실행 시간 중앙값 | Buffers |
| --------: | --------------- | :-----: | --------: | ------: |
|        50 | Seq Scan        |    O    |   0.065ms |       7 |
|       100 | Index Only Scan |    X    |   0.056ms |      25 |
|       200 | Index Only Scan |    X    |   0.065ms |      25 |
|       500 | Index Only Scan |    X    |   0.066ms |      26 |
|     1,000 | Index Only Scan |    X    |   0.076ms |      26 |
|    10,000 | Index Only Scan |    X    |   0.068ms |       6 |

처음 예상했던 것과 다른 부분이 있었다.

Room에 장소가 50개 있을 때는 본인이 만든 복합 인덱스를 사용하지 않고 `Seq Scan`과 `Sort`를 선택했다.

처음 결과를 봤을 때는 인덱스를 사용하지 않았으니 문제가 있는 것 아닌가 생각했다.

하지만 테이블이 매우 작을 때는 인덱스를 따라가는 것보다 전체 데이터를 읽고 정렬하는 편이 PostgreSQL이 계산한 비용상 더 저렴할 수 있다는 것이다!

PostgreSQL 공식 문서에서도 테이블이 너무 작을 때는 인덱스를 사용하는 것보다 순차 스캔이 더 저렴할 수 있다는 예제를 확인할 수 있었다. 따라서 Seq Scan이 나타났다는 사실만으로 쿼리가 잘못되었다고 판단해서는 안 되는 것 같았다.

그래서 50개 정도의 작은 데이터에서는 PostgreSQL이 `Seq Scan + Sort`를 더 저렴한 방법으로 판단한 것으로 이해했다.

장소가 100개로 늘어난 뒤부터는 본인이 정의한 `idx_room_places_room_created_id_desc`를 이용한 `Index Only Scan`이 나타났다.

```text
Limit
  -> Index Only Scan using idx_room_places_room_created_id_desc
       Index Cond: (room_id = ...)
```

그리고 Room의 장소를 10,000개까지 늘려도 핵심 목록 쿼리의 실행 시간은 약 0.06~0.08ms 사이에서 측정되었다.

처음에는 데이터가 열 배씩 늘어나면 조회 시간도 어느 정도 함께 늘어날 것이라고 예상했다.

하지만 이번 결과에서는 그런 경향이 뚜렷하게 나타나지 않았다.

내가 작성한 쿼리는 최신 장소 21개만 필요하다. 복합 인덱스에서 조건에 맞는 최신 데이터 21개를 찾으면 더 이상 Room의 나머지 장소를 모두 읽을 필요가 없기 때문인 것 같다.

적어도 이번 실험 범위에서는 Room에 저장된 전체 장소 수보다 `LIMIT 21`과 복합 인덱스가 목록 조회 비용에 더 큰 영향을 주고 있다고 판단했다.

## 그런데 count 쿼리는 달랐다

현재 장소 목록 API는 장소 목록만 반환하지 않는다.

응답에 `roomPlaceTotalCount`를 포함하기 위해 매 요청마다 다음과 같은 count 쿼리도 실행한다.

```sql
SELECT count(*)
FROM room_places
WHERE room_id = :room_id;
```

결과는 다음과 같았다.

| Room 장소 수 | 실행 시간 중앙값 | 실행 계획    |
| --------: | --------: | -------- |
|        50 |   0.055ms | Seq Scan |
|       100 |   0.062ms | Seq Scan |
|       200 |   0.079ms | Seq Scan |
|       500 |   0.120ms | Seq Scan |
|     1,000 |   0.172ms | Seq Scan |
|    10,000 |   1.208ms | Seq Scan |

목록 조회 쿼리는 필요한 21개의 장소를 찾은 뒤 멈출 수 있다.

반면 정확한 전체 개수를 구하려면 해당 Room에 속한 행이 몇 개인지 확인해야 한다. 그래서 Room의 장소 수가 늘어날수록 실행 시간도 함께 증가한 것으로 보였다.

10,000개일 때도 1.208ms이므로 현재 환경에서는 여전히 매우 작은 시간이다.

다만 목록 쿼리와 달리 데이터 개수에 따라 비용이 증가하는 지점이 실제로 존재한다는 것은 확인할 수 있었다.


## 실제 API는 얼마나 걸렸을까?

DB 쿼리만 확인한 뒤, 동일한 데이터 구간에서 실제 장소 목록 API도 호출했다.

```http
GET /api/v1/rooms/{roomId}/places?limit=20
```

측정 결과는 다음과 같았다.

| Room 장소 수 |      p50 |      p95 |      p99 | 300회 중 최대 |
| --------: | -------: | -------: | -------: | --------: |
|        50 | 16.475ms | 18.855ms | 19.571ms |  36.640ms |
|       100 | 16.807ms | 19.749ms | 30.299ms |  40.514ms |
|       200 | 16.938ms | 18.826ms | 33.942ms |  41.200ms |
|       500 | 17.133ms | 22.000ms | 34.285ms |  41.136ms |
|     1,000 | 17.275ms | 32.992ms | 37.147ms |  40.269ms |
|    10,000 | 17.796ms | 20.542ms | 39.025ms |  43.575ms |

결과를 보고 가장 먼저 눈에 들어온 것은 1,000개의 p95였다.

1,000개의 p95가 10,000개보다 높게 측정되었다.

데이터가 열 배로 늘었는데 오히려 더 빨라진 것처럼 보였다.

하지만 이 결과만으로 10,000개가 1,000개보다 빠르다고 해석할 수는 없었다.

이번 측정은 localhost에서 진행했다. 같은 PC에서 DB와 애플리케이션, 측정 스크립트가 모두 실행되고 있었고, JVM 상태나 GC, 운영체제 스케줄링, 백그라운드 프로세스 등의 영향을 완전히 통제하지 못했다.

수 ms 단위의 차이에는 이러한 환경적 잡음이 섞였을 가능성이 높다고 생각했다.

이번 실험에서는 장소가 50개에서 10,000개까지 늘어났지만, p50은 약 16~17ms 사이에 머물렀다. p95와 p99에는 다소 흔들림이 있었지만 데이터 개수에 비례해 계속 증가하는 모습은 보이지 않았다.

한 Room에 장소가 10,000개 있을 때도 p95는 약 20.5ms로 측정되었다.

물론 이 결과는 로컬 순차 요청 환경에서 나온 값이다.

운영 서버나 네트워크 환경, 동시 요청 상황에서도 같은 결과가 나온다고 단정할 수는 없다.

다만 적어도 이번 테스트에서는 200개나 500개에서 장소 저장을 막아야 할 만큼 목록 API가 느려지는 현상을 발견하지 못했다.


# 그러면 굳이 저장 제한을 두지 않아도 되는 것 아닌가?

별로 안 느려지는 것 같은데....

> 10,000개에서도 이 정도라면 그냥 제한을 두지 않아도 되는 것 아닌가?

적어도 이번에 측정한 장소 목록 API만 놓고 보면 그렇다고 생각한다.

처음에는 Room당 저장 상한을 200개와 500개 중 하나로 정하고, 이를 코드에 적용하는 것이 이번 리팩토링의 결론이 될 것이라고 예상했다.

하지만 실제 측정 결과에서는 둘 중 하나를 선택해야 할 성능상 이유를 찾지 못했다.

이번 실험에서는 한 Room에 장소가 10,000개 있을 때도 핵심 목록 쿼리와 API 응답 시간이 크게 증가하지 않았다.

그렇다고 `어디더라는 장소를 무제한으로 저장해도 영원히 괜찮다`고 결론 내릴 수는 없다!

* 데이트 코스 생성은 Room에 저장된 여러 장소를 후보군으로 사용한다.
* 정확한 count 쿼리의 비용은 Room 장소 수와 함께 증가했다.
* 장소가 계속 쌓이면 저장 공간과 백업, 복구에 필요한 데이터도 증가한다.
* 비정상적인 클라이언트나 버그가 짧은 시간에 대량 저장을 발생시킬 수도 있다.
* 이번 테스트는 순차 호출이므로 동시 요청이 많은 상황은 검증하지 않았다.

Room에 장소가 10,000개 있어도 목록에서는 21개만 가져오므로 빠를 수 있다. 하지만 코스 생성에서 후보 장소를 많이 읽거나 비교한다면 전혀 다른 결과가 나올 수 있다.

그래서 이번 리팩토링에서는 Room당 200개나 500개의 하드 제한을 바로 추가하지 않기로 했다.

실제 운영을 시작한 뒤 Room별 장소 수와 API 응답 시간, 지도 및 코스 생성 비용을 관찰해 상한이 필요하다고 판단된다면 그때 다시 정할 수 있을 것이다.

운영상 최소한의 안전장치가 반드시 필요하다면 일반 사용자가 쉽게 도달하기 어려운 10,000개 정도를 임시 guardrail로 둘 수도 있다.

하지만 이것 역시 `성능 한계가 10,000개다`라는 의미는 아니다.

이번에 검증한 범위를 넘어 데이터가 예상치 못하게 폭발하는 상황을 막기 위한 방어선일 뿐이다.

현재로서는 그 guardrail조차 바로 추가하기보다, 먼저 지도와 코스 생성 비용을 확인하는 편이 낫다고 판단했다.


## 성능 개선을 하지 못한 걸까?

처음에는 장소 수를 제한하고, 그 제한을 코드에 적용하는 것까지가 이번 리팩토링이라고 생각했다.

그런데 측정 결과가 예상과 다르게 나왔는데도 처음 생각했던 결론을 그대로 밀어붙인다면, 굳이 테스트를 진행한 의미가 없을 것 같았다.

이번에 새로운 인덱스를 추가하지도 않았고, Room당 저장 제한도 추가하지 않았다.

그래도 본인이 작성한 코드에 대해 이전보다 분명하게 알게 된 부분은 있다.

* 장소 목록용 복합 인덱스가 실제 쿼리에서 사용되고 있었다.
* 데이터가 매우 적을 때는 `Seq Scan + Sort`가 선택되기도 했다.
* 커서 페이지네이션은 50번째 페이지에서도 눈에 띄는 성능 저하가 없었다.
* 목록 핵심 쿼리는 한 Room에 장소가 10,000개 있을 때도 비슷한 비용을 유지했다.
* 정확한 전체 개수를 구하는 count 쿼리는 Room의 장소 수와 함께 비용이 증가했다.

성능 개선이라고 해서 항상 코드를 바꿔야 하는 것은 아닌 것 같다.

본인은 처음에 데이터가 쌓이면 목록 API가 느려질 것이라고 예상했다. 하지만 직접 측정해 보니 현재의 커서 페이지네이션과 복합 인덱스가 생각보다 잘 동작하고 있었다.

필요하지 않은 것을 추가하지 않기로 결정한 것 역시 이번 리팩토링에서 얻은 결과라고 생각한다.
